honeyconf.sh

System configuration management, as simple as can be. Describe your machines in one YAML file, compile each one into a plain bash script, and pipe it over SSH.

Pure bash yq + jq at compile time Nothing installed on targets Debian / Ubuntu Tested with bats

Easy to modify

Every feature is a small shell script under emitters/. Adding one is adding a file.

Simple mapping to shell

The output is the exact bash that will run, so you can read it, diff it and review it before anything changes.

Idempotent

Generated scripts check before they act, so running a deploy twice is safe and quick.

Agentless

Targets only need SSH, sudo and bash. No daemon, no Python, no runtime.

How it works#

honeyconf.sh works like a small compiler. Your machines.yaml is the source, each emitter is a compiler pass, and the result is a self-contained bash script that serves as the intermediate representation. Deploying means streaming that script to sudo /bin/bash on the target over SSH.

machines.yamlDeclarative description of every machine
→
compile.shRuns each emitter for one machine
→
script.shPlain, readable, idempotent bash
→
ssh … sudo bashdeploy.sh streams it to the target

Emitters and their order

Every compiled script starts with #!/bin/bash and set -eu, so it stops at the first failing command or unset variable. Then come a few helper functions, then the output of each emitter in this fixed order. Each emitter wraps its output in # BEGIN: name / # END: name markers so the script is easy to scan.

#EmitterRuns whenWhat it does
1common_toolsAlwaysDefines ensure_apt_fresh, ensure_installed and halt_intervention_required
2hostnameoptions.manage_hostname ≠ falseSets the hostname to the machine key
3system_packagessystem.packages is setInstalls apt packages
4system_filessystem.files is setWrites whole files
5swapswap is setCreates and enables /swapfile
6ssh_authorized_keysaccess_control is setWrites the admin user's authorized_keys
7volumesmounts is setOpens LUKS devices, mounts ext4 volumes, imports zpools, creates datasets
8networkingnetwork is setWrites netplan or ifupdown config and reloads the network
9ensure_docker_runningRole application_serverStarts docker.service if installed
10ssh_password_authenticationoptions.disable_ssh_password_authentication ≠ falseForces PasswordAuthentication no
11fail2banoptions.manage_fail2ban ≠ falseInstalls fail2ban
12updatedboptions.manage_updatedb ≠ falseStops locate from indexing /mnt and aufs
13monitoringmonitoring.type: node_exporterInstalls Prometheus node_exporter with mutual TLS
14application_server_roleRole application_serverInstalls Docker and makes it wait for mounts
15service_accountsaccess_control.service_accounts is setCreates users, groups, sudo rules and SSH keys

Service accounts come last on purpose: groups such as docker only exist after the application server role has run.

Helper functions in every script

The first part of every compiled script is the same. Emitters call these functions instead of running apt-get directly:

ensure_apt_fresh() { if test -z "$(find /var/cache/apt/pkgcache.bin -mmin -60)"; then apt-get update -q fi } ensure_installed() { local packages=$* for package in $packages; do if ! dpkg -l $package | grep -q '^ii'; then ensure_apt_fresh DEBIAN_FRONTEND=noninteractive apt-get -y -q install $package fi done } halt_intervention_required() { echo "************************************************************" cat - echo "************************************************************" echo "PROCESS HALTED. Human intervention required" exit 101 }
  • ensure_installed pkg… installs only the packages that are missing, so a run where everything is already installed makes no apt calls.
  • ensure_apt_fresh runs apt-get update only when the package cache is older than one hour.
  • halt_intervention_required prints instructions from standard input and exits with code 101. See Exit codes.

Installation#

There is nothing to build or install system-wide. The recommended setup is to keep your machines.yaml in its own Git repository and have a Makefile download a pinned honeyconf.sh release into .vendor/. Every clone of your infrastructure repository then uses the same version, and upgrading is a one-line change you can review.

Recommended: vendor a release with make

A typical infrastructure repository:

infrastructure/ ├── Makefile ├── .gitignore ├── machines.yaml └── .vendor/ # created by make, not committed ├── honeyconf-3.1.0.sh/ # extracted release └── honeyconf.sh -> honeyconf-3.1.0.sh

The Makefile downloads the tagged release, extracts it into a versioned folder, and points a stable .vendor/honeyconf.sh symlink at it:

.PHONY: clean all: .vendor/honeyconf.sh clean: rm -rf .vendor .vendor: mkdir -p .vendor .vendor/honeyconf-3.1.0.sh: | .vendor mkdir -p $@ wget https://github.com/bee-software/honeyconf.sh/archive/refs/tags/v3.1.0.tar.gz -O $@/honeyconf.tar.gz tar -xvzf $@/honeyconf.tar.gz -C $@ --strip-components=1 .vendor/honeyconf.sh: .vendor/honeyconf-3.1.0.sh ln -sf honeyconf-3.1.0.sh $@

The | makes .vendor an order-only prerequisite: it must exist, but its timestamp is ignored. Without it, creating the symlink updates the folder's timestamp and every make downloads the release again.

Recipes must be indented with tabsmake rejects recipe lines indented with spaces (missing separator). The copy button keeps the tabs, but some editors turn them into spaces when you paste.
.vendor/

Fetch honeyconf.sh, then call the scripts through the symlink:

make .vendor/honeyconf.sh/compile.sh machines.yaml web1.example.com .vendor/honeyconf.sh/deploy.sh machines.yaml '^web1\.example\.com$'

The rest of this page uses these .vendor/honeyconf.sh/… paths. Running make again does nothing once the release is downloaded, so you can make it the first step of any CI job or deploy script.

Upgrading

Replace every 3.1.0 in the Makefile with the new version (see the list of releases), then rebuild from scratch:

make clean && make
Why make clean first?If the old .vendor/honeyconf.sh symlink is still there, ln -sf follows it and creates the new link inside the old release folder instead of replacing it. Starting from a clean .vendor avoids this.

Before deploying a new version, compile each machine with the old and new versions and compare the scripts, so you see exactly what the upgrade will change.

Alternative: clone the repository

To try honeyconf.sh or work on it, clone it and run the scripts directly:

git clone https://github.com/bee-software/honeyconf.sh.git honeyconf.sh/compile.sh machines.yaml web1.example.com

On your workstation

ToolNeeded forNotes
yqCompilingVersion 4+ recommended. Version 3.4 also works.
jqCompilingUsed for every lookup in machines.yaml.
bash, sshDeployingAny recent bash and OpenSSH client.
bats-coreRunning testsOr use Docker with make test.

On target machines

  • Debian or Ubuntu (the scripts use apt-get, dpkg and adduser) with systemd.
  • An SSH account named in credentials.username that can run sudo /bin/bash without a password prompt.
  • Network access to your apt mirrors. With monitoring.source: upstream-1.2.2, it also needs access to GitHub.

Quick start#

1. Describe a machine

Create a machines.yaml. Each key under machines is the hostname used for SSH, and it also becomes the machine's hostname.

machines: web1.example.com: credentials: username: localadmin access_control: authorized_keys_user: localadmin authorized_keys: | ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIExample alice@laptop

2. Compile and read the script

Compiling only reads the YAML. It never connects to the machine, so you can review the result first.

.vendor/honeyconf.sh/compile.sh machines.yaml web1.example.com

This machine sets no options, so the hostname, SSH hardening, fail2ban and updatedb emitters all run by default:

# BEGIN: hostname echo "web1.example.com" > /etc/hostname hostname web1.example.com grep '^127.0.1.1' /etc/hosts | grep -q 'web1.example.com' || sed -i 's/^\(127.0.1.1\s.*\)/\1 web1.example.com/g' /etc/hosts # END: hostname # BEGIN: ssh_authorized_keys mkdir -p "/home/localadmin/.ssh" cat <<EOF > /home/localadmin/.ssh/authorized_keys # # This file is managed by an automated provisioning task. Any manual change will eventually be overwritten. # ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIExample alice@laptop EOF chmod 644 /home/localadmin/.ssh/authorized_keys # END: ssh_authorized_keys # BEGIN: ssh_password_authentication if ! grep -qi '^PasswordAuthentication no' /etc/ssh/sshd_config; then sed -i '/^PasswordAuthentication/Id' /etc/ssh/sshd_config echo 'PasswordAuthentication no' >> /etc/ssh/sshd_config systemctl reload ssh.service fi # END: ssh_password_authentication # BEGIN: fail2ban ensure_installed fail2ban # END: fail2ban # BEGIN: updatedb if [ -f /etc/updatedb.conf ]; then . /etc/updatedb.conf if [ "$PRUNEPATHS" == "${PRUNEPATHS/\/mnt/}" ]; then sed -i '/PRUNEPATHS/c\PRUNEPATHS="'"$PRUNEPATHS /mnt"'"' /etc/updatedb.conf fi if [ "$PRUNEFS" == "${PRUNEFS/aufs/}" ]; then sed -i '/PRUNEFS/c\PRUNEFS="'"$PRUNEFS aufs"'"' /etc/updatedb.conf fi fi # END: updatedb

3. Deploy

.vendor/honeyconf.sh/deploy.sh machines.yaml web1.example.com
web1.example.com: #!/bin/bash web1.example.com: set -eu web1.example.com: + set -eu … web1.example.com: OK

Every line is prefixed with the machine name. The script runs with bash -vx, so you see each command as it runs. If anything fails, the deploy stops and OK is not printed.

Command reference#

All commands can be run from any directory. Each one finds its helpers relative to its own location.

compile.sh

.vendor/honeyconf.sh/compile.sh <machines.yaml> <machine-name>

Writes the full script for one machine to standard output. The machine name must match a key under machines exactly. Exits with code 1 if the machine is missing or the YAML is invalid. Compiling ignores managed: false.

# Save a script and review it .vendor/honeyconf.sh/compile.sh machines.yaml web1.example.com > web1.sh less web1.sh # See what a configuration change will do git stash && .vendor/honeyconf.sh/compile.sh machines.yaml web1.example.com > before.sh git stash pop && .vendor/honeyconf.sh/compile.sh machines.yaml web1.example.com > after.sh diff -u before.sh after.sh

deploy.sh

.vendor/honeyconf.sh/deploy.sh <machines.yaml> <hostname-pattern> [identity-file]

Compiles and runs the script on every managed machine whose name matches <hostname-pattern>, one machine at a time.

  • Pattern: a grep regular expression matched against machine names (see list_machines.sh).
  • Login: ssh -l <credentials.username> <machine> sudo /bin/bash -vx.
  • Identity file: the optional third argument is passed to SSH as -i.
  • Failure: the first machine that fails stops the run. Machines after it are not touched.
# One machine .vendor/honeyconf.sh/deploy.sh machines.yaml '^web1\.example\.com$' # All web servers, with a specific key .vendor/honeyconf.sh/deploy.sh machines.yaml '^web' ~/.ssh/ops_ed25519 # Everything that is managed .vendor/honeyconf.sh/deploy.sh machines.yaml .
Patterns are substringsweb1 also matches web10.example.com. Use ^ and $ and escape the dots when you mean a single machine.

execute.sh

.vendor/honeyconf.sh/execute.sh <machines.yaml> <hostname-pattern> <commands-file>

Runs any shell file as root on the matching machines, using the same SSH login as deploy.sh. It prints <machine>: DONE after each one. This is useful for one-off maintenance that should not be part of the configuration.

.vendor/honeyconf.sh/execute.sh machines.yaml '^db' .vendor/honeyconf.sh/commands/apt_upgrade.sh

list_machines.sh

.vendor/honeyconf.sh/list_machines.sh <machines.yaml> <hostname-pattern>

Prints the managed machines that match the pattern, in file order. Machines with managed: false are skipped. The other commands use this to pick their targets, so run it first to check what a pattern will hit.

$ .vendor/honeyconf.sh/list_machines.sh machines.yaml example.com web1.example.com app.example.com # legacy.example.com is not listed: it has managed: false

profile_all.sh

.vendor/honeyconf.sh/profile_all.sh <machines.yaml> <hostname-pattern> > inventory.tsv

Collects facts from each matching machine and prints a tab-separated table you can paste into a spreadsheet. Columns:

ColumnSource on the machine
Machine nameKey in machines.yaml
Hostname (long)hostname -f
Operating systemlsb_release -d -s
Kernel releaseuname -r
Aptapt-check: pending updates;security updates (or -)
Reboot?Whether /var/run/reboot-required exists
Date of last bootuptime -s
Docker versiondocker --version
Docker-compose versiondocker-compose --version

machines.yaml reference#

The file has one top-level key, machines. Under it, each key is a machine name: the SSH target and the hostname. Keys may contain letters, digits, ., _ and -.

machines: host.example.com: managed: true # include in deploy / execute / profile runs credentials: {} # SSH login options: {} # turn default behaviours off roles: [] # application_server system: {} # packages and files swap: {} # swap file access_control: {} # SSH keys and service accounts mounts: {} # disks: ext4, LUKS, ZFS network: {} # dmz / internal / public / dialin monitoring: {} # prometheus node_exporter

An empty machine (host.example.com: {}) is valid. It still gets the default hostname, SSH hardening, fail2ban and updatedb steps.

Reusing values with YAML anchorsAnchors and aliases work, so you can share blocks between machines. Keys outside machines are ignored, which makes them a good place for anchors:
x-admin-keys: &admin_keys authorized_keys_user: localadmin authorized_keys: | ssh-ed25519 AAAA… alice@laptop machines: web1.example.com: access_control: *admin_keys web2.example.com: access_control: *admin_keys

Machine & credentials

KeyTypeDefaultDescription
managedbooleantrueSet to false to leave a machine out of deploy.sh, execute.sh and profile_all.sh while keeping it in the inventory.
credentials.usernamereqstring—SSH login. It needs passwordless sudo. Required for deploy.sh, execute.sh and profile_all.sh.
credentials.passwordstring—Allowed for your own records. honeyconf.sh never uses it.
machines: web1.example.com: credentials: username: localadmin old-nas.example.com: managed: false # documented, but never deployed to credentials: username: admin

options

Turns the default behaviours on or off. All four are on unless you set them to false.

KeyDefaultWhen enabled
manage_hostnametrueWrites the machine key to /etc/hostname, applies it with hostname, and adds it to the 127.0.1.1 line of /etc/hosts.
disable_ssh_password_authenticationtrueRemoves any PasswordAuthentication line from sshd_config, appends PasswordAuthentication no and reloads sshd. Does nothing if the setting is already correct.
manage_fail2bantrueInstalls fail2ban with its default jails.
manage_updatedbtrueAdds /mnt to PRUNEPATHS and aufs to PRUNEFS in /etc/updatedb.conf, so locate doesn't crawl your volumes and Docker layers.
machines: defaults.example.com: {} # all four options left on
# BEGIN: hostname echo "defaults.example.com" > /etc/hostname hostname defaults.example.com grep '^127.0.1.1' /etc/hosts | grep -q 'defaults.example.com' || sed -i 's/^\(127.0.1.1\s.*\)/\1 defaults.example.com/g' /etc/hosts # END: hostname # BEGIN: ssh_password_authentication if ! grep -qi '^PasswordAuthentication no' /etc/ssh/sshd_config; then sed -i '/^PasswordAuthentication/Id' /etc/ssh/sshd_config echo 'PasswordAuthentication no' >> /etc/ssh/sshd_config systemctl reload ssh.service fi # END: ssh_password_authentication # BEGIN: fail2ban ensure_installed fail2ban # END: fail2ban # BEGIN: updatedb if [ -f /etc/updatedb.conf ]; then . /etc/updatedb.conf if [ "$PRUNEPATHS" == "${PRUNEPATHS/\/mnt/}" ]; then sed -i '/PRUNEPATHS/c\PRUNEPATHS="'"$PRUNEPATHS /mnt"'"' /etc/updatedb.conf fi if [ "$PRUNEFS" == "${PRUNEFS/aufs/}" ]; then sed -i '/PRUNEFS/c\PRUNEFS="'"$PRUNEFS aufs"'"' /etc/updatedb.conf fi fi # END: updatedb

To turn every default off, for example on a machine you only want to give swap to:

options: manage_hostname: false manage_fail2ban: false manage_updatedb: false disable_ssh_password_authentication: false
Before you disable password loginsCheck that key-based login works for credentials.username first, by setting access_control in the same file. Otherwise you can lock yourself out.

system

KeyTypeDescription
system.packagesstring[]Apt packages to install if missing. Packages are never removed or upgraded.
system.filesobject[]Files written in full on every deploy.
system.files[].pathreqstringAbsolute path. The parent directory must already exist.
system.files[].contentsstringFile contents. Use a YAML block scalar (|).
machines: packages.example.com: system: packages: [htop, curl, unattended-upgrades] files: - path: /etc/motd contents: | Managed by honeyconf.sh — local changes will be overwritten.
# BEGIN: system_packages ensure_installed htop ensure_installed curl ensure_installed unattended-upgrades # END: system_packages # BEGIN: system_files cat <<EOF > /etc/motd Managed by honeyconf.sh — local changes will be overwritten. EOF # END: system_files
Shell expansion inside file contentsContents go into an unquoted heredoc (cat <<EOF), so the target's shell expands $VARIABLES, $(commands) and backticks when the script runs. Write \$ and \` wherever you need them literally, for example in shell scripts or systemd units. The same applies to authorized_keys and monitoring certificates.
system: files: - path: /etc/profile.d/prompt.sh contents: | export PS1="[\$(hostname -s)] \w \$ "

swap

KeyTypeDescription
swap.size_mbreqintegerSize of /swapfile in MB.

Creates /swapfile, adds it to /etc/fstab, turns it on, and sets vm.swappiness=10 if no swappiness is configured yet.

machines: swap.example.com: swap: size_mb: 2048
# BEGIN: swap if ! test -f /swapfile; then fallocate -l 2048M /swapfile chmod 600 /swapfile mkswap /swapfile fi if ! grep -q '^/swapfile swap' /etc/fstab; then echo "/swapfile swap swap defaults 0 0" >> /etc/fstab fi if ! swapon --show=name --noheadings | grep -q '^/swapfile$'; then swapon /swapfile fi if ! grep -q '^vm.swappiness=' /etc/sysctl.conf; then echo 'vm.swappiness=10' >> /etc/sysctl.conf sysctl -p fi # END: swap
Changing the size laterThe file is only created when it does not exist, so editing size_mb later has no effect. To resize, run swapoff /swapfile && rm /swapfile on the machine and deploy again.

access_control

Manages the authorized_keys file of the admin account, usually the same user as credentials.username. The file is overwritten on every deploy, so honeyconf.sh is the only source of truth for who can log in.

KeyTypeDescription
authorized_keysstringPublic keys, one per line.
authorized_keys_additionalstringMore keys appended after authorized_keys. Useful to add per-machine keys to a shared anchor.
authorized_keys_userstringWrites to /home/<user>/.ssh/authorized_keys.
authorized_keys_filestringExplicit path. Takes precedence over authorized_keys_user. Use it for root or for users whose home is not under /home.
service_accountsobject[]See Service accounts.
You must set authorized_keys_user or authorized_keys_fileIf access_control exists but neither key is set, compiling fails. This includes the case where you only define service_accounts.
machines: keys.example.com: access_control: authorized_keys_user: localadmin authorized_keys: | ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIExample alice@laptop authorized_keys_additional: | ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIExample bob@laptop

Service accounts

Creates local accounts for automation, such as a CI user that runs docker compose. Accounts are created without a password and are never deleted.

KeyTypeDefaultDescription
usernamereqstring—Created with adduser --disabled-password if it does not exist.
homereqstring—Home directory.
groupsstring[][]Extra groups, added with usermod -aG. The groups must already exist. Groups are only added, never removed.
sudobooleanfalsetrue writes /etc/sudoers.d/service_account_<user> granting NOPASSWD:ALL, checked with visudo before it is installed. false deletes that file.

machines: svc.example.com: access_control: authorized_keys_file: /root/.ssh/authorized_keys authorized_keys: | ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIExample alice@laptop service_accounts: - username: deploy home: /home/deploy groups: [docker] sudo: true authorized_keys: | ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIExample ci@runner - username: backup home: /var/lib/backup
# BEGIN: ssh_authorized_keys mkdir -p "/root/.ssh" cat <<EOF > /root/.ssh/authorized_keys # # This file is managed by an automated provisioning task. Any manual change will eventually be overwritten. # ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIExample alice@laptop EOF chmod 644 /root/.ssh/authorized_keys # END: ssh_authorized_keys # BEGIN: service_accounts # deploy local account if ! grep -q '^deploy:' /etc/passwd; then adduser --disabled-password --gecos "" --home /home/deploy deploy fi usermod -aG docker deploy cat <<EOF > /etc/sudoers.d/service_account_deploy.tmp # # This file is managed by an automated provisioning task. Any manual change will eventually be overwritten. # deploy ALL=(ALL) NOPASSWD:ALL EOF visudo -cf /etc/sudoers.d/service_account_deploy.tmp chmod 0440 /etc/sudoers.d/service_account_deploy.tmp mv /etc/sudoers.d/service_account_deploy.tmp /etc/sudoers.d/service_account_deploy if ! test -d /home/deploy/.ssh; then mkdir -p /home/deploy/.ssh chmod 0700 /home/deploy/.ssh fi cat <<EOF > /home/deploy/.ssh/authorized_keys # # This file is managed by an automated provisioning task. Any manual change will eventually be overwritten. # ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIExample ci@runner EOF chmod 0644 /home/deploy/.ssh/authorized_keys chown -R deploy:deploy /home/deploy/.ssh/ # backup local account if ! grep -q '^backup:' /etc/passwd; then adduser --disabled-password --gecos "" --home /var/lib/backup backup fi rm -f /etc/sudoers.d/service_account_backup # END: service_accounts
Taking sudo awayTo revoke sudo, set sudo: false or remove the key, then deploy. Removing the whole account from the YAML leaves both the user and its sudoers file on the machine.

mounts — ext4 and LUKS

Each key under mounts is a volume name. Volumes that are not ZFS are mounted at /mnt/external_storage/<name> through an /etc/fstab entry with noauto, so a missing disk never blocks booting. Every deploy mounts them again.

KeyTypeDefaultDescription
devicestring—Block device, for example /dev/sdb or /dev/disk/by-id/….
devicesstring[]—Takes precedence over device. Non-ZFS volumes only mount the first one.
filesystemstringext4Written to fstab as-is (ext4, xfs, …). zfs works differently: see ZFS. The filesystem must already exist on the device.
encryptedbooleanfalseOpens each device as a LUKS container named after the volume (<name>, <name>_1, …) and uses /dev/mapper/<name>.
encryption_keystring—LUKS passphrase.
foldersstring[]—Subfolders created inside the mountpoint.
machines: ext4.example.com: mounts: data: device: /dev/sdb encrypted: true encryption_key: correct-horse-battery-staple folders: [postgres, uploads]
# BEGIN: volumes_data ensure_installed cryptsetup if cryptsetup status data | grep -q 'inactive'; then if cryptsetup isLuks /dev/sdb; then echo 'correct-horse-battery-staple' | cryptsetup --key-file - open /dev/sdb data else halt_intervention_required <<"LUKS_INIT" Device /dev/sdb does not appear to be a LUKS device. If you are initializing a new device, please format the LUKS container using the following command: echo 'correct-horse-battery-staple' | cryptsetup --key-file - luksFormat /dev/sdb WARNING: All data will be lost! LUKS_INIT fi fi mkdir -p /mnt/external_storage/data if ! grep -q '/mnt/external_storage/data' /etc/fstab; then echo "/dev/mapper/data /mnt/external_storage/data ext4 defaults,noauto 0 0" >> /etc/fstab fi mountpoint -q /mnt/external_storage/data || mount /mnt/external_storage/data mkdir -p /mnt/external_storage/data/postgres mkdir -p /mnt/external_storage/data/uploads # END: volumes_data
Setting up a new encrypted diskhoneyconf.sh never formats a disk. On a blank device, the deploy stops with code 101 and prints the cryptsetup luksFormat command to run. Run it, create the filesystem on /dev/mapper/<name> (for example mkfs.ext4 /dev/mapper/data), then deploy again.

mounts — ZFS

With filesystem: zfs, the volume name is the pool name. honeyconf.sh installs zfsutils-linux and zfs-auto-snapshot, imports the pool, then creates and mounts each dataset. Combine with encrypted: true to build the pool on LUKS devices.

KeyTypeDescription
devices / devicestring[] / stringPool members. Used in the suggested zpool create command.
datasets[].namereqstringDataset name, created as <pool>/<name>.
datasets[].mountpointreqstringUpdated whenever it differs from the configuration.
datasets[].compressionstringFor example lz4, zstd or off. Updated whenever it differs.
datasets[].encryptionstringNative ZFS encryption, for example on or aes-256-gcm. Can only be set when the dataset is created.
datasets[].encryption_passphrasestringUsed to create the dataset and to load its key on every deploy.
machines: zfs.example.com: mounts: tank: filesystem: zfs devices: [/dev/sdb, /dev/sdc] datasets: - name: backups mountpoint: /srv/backups compression: zstd - name: secrets mountpoint: /srv/secrets encryption: aes-256-gcm encryption_passphrase: another-long-passphrase
# BEGIN: volumes_tank ensure_installed zfsutils-linux zfs-auto-snapshot if ! zpool status tank; then if ! zpool import tank; then halt_intervention_required <<"ZPOOL_INIT" tank does not appear to be a zpool. If you are initializing a new device, please create a zpool using the following command: zpool create -O compression=lz4 -O atime=off tank /dev/sdb /dev/sdc ZPOOL_INIT fi fi zfs create -p tank/backups if [ "$(zfs get mountpoint -H -o value tank/backups)" != "/srv/backups" ]; then zfs set mountpoint=/srv/backups tank/backups fi if [ "$(zfs get compression -H -o value tank/backups)" != "zstd" ]; then zfs set compression=zstd tank/backups fi if [ "$(zfs get mounted -H -o value tank/backups)" != "yes" ]; then zfs mount tank/backups fi echo -n 'another-long-passphrase' | zfs create -p -o encryption=aes-256-gcm -o keylocation=prompt -o keyformat=passphrase tank/secrets if [ "$(zfs get mountpoint -H -o value tank/secrets)" != "/srv/secrets" ]; then zfs set mountpoint=/srv/secrets tank/secrets fi if [ "$(zfs get keystatus -H -o value tank/secrets)" != "available" ]; then echo -n 'another-long-passphrase' | zfs load-key tank/secrets fi if [ "$(zfs get mounted -H -o value tank/secrets)" != "yes" ]; then zfs mount tank/secrets fi # END: volumes_tank
Pool layout is up to youThe suggested zpool create command stripes all devices. If you want a mirror or raidz, create the pool by hand (for example zpool create … tank mirror /dev/sdb /dev/sdc) and deploy again. Since the pool then exists, it is imported and used as-is.

network

Up to four networks are supported, each with a fixed name and config file. Other names are ignored.

NetworkFile keyTypical use
public99-wan-networkInternet-facing interface. Managing it also turns off cloud-init network config.
internal99-internal-networkPrivate LAN or VPC.
dmz99-dmz-networkSemi-trusted segment.
dialin99-dialin-networkOut-of-band or remote-access link.
KeyTypeDefaultDescription
managedbooleanfalseOnly networks with managed: true are written. Unmanaged entries are documentation only.
interfacestring—For example eth0 or ens18.
modeenumstaticstatic, dhcp or manual.
stateenumupdown sets the mode to manual, leaves out auto, and stops ifup@<interface>.
ipstring—CIDR address such as 10.0.0.10/24. Used in static mode.
gatewaystring—Default gateway. Set it on one network only.
routes[]object[]—Static routes, each with net (CIDR) and gateway.
nameserversstring[]—DNS servers. They are also written to /etc/dhcp/dhclient.conf as supersede domain-name-servers.

Each managed network is written in both formats, but each one is only applied if its directory exists. Netplan machines get /etc/netplan/<key>.yaml and ifupdown machines get /etc/network/interfaces.d/<key>.cfg. The same configuration therefore works on old and new Ubuntu releases. The network is then reloaded with systemctl restart networking or netplan apply.

Test network changes firstA wrong address or gateway can cut off your SSH session halfway through a deploy. Compile and read the output before deploying, and make sure you have console access, especially for the public interface.
cloud-initIf public.managed is true, honeyconf.sh writes 99-disable-network-config.cfg and deletes cloud-init's own network files so they don't conflict. If not, it removes that file and cloud-init manages the network again.

roles

RoleEffect
application_serverInstalls docker.io and docker-compose-v2 if dockerd is missing, and starts docker.service. For every volume in mounts, it adds a systemd drop-in that makes Docker require the mount and start after it. If a disk is missing, Docker then refuses to start, instead of starting containers that write into an empty mountpoint.
backup_serverAccepted as a label for your own tooling. It has no effect yet.
machines: app.example.com: roles: [application_server] mounts: data: device: /dev/sdb
# BEGIN: volumes_data mkdir -p /mnt/external_storage/data if ! grep -q '/mnt/external_storage/data' /etc/fstab; then echo "/dev/sdb /mnt/external_storage/data ext4 defaults,noauto 0 0" >> /etc/fstab fi mountpoint -q /mnt/external_storage/data || mount /mnt/external_storage/data # END: volumes_data # BEGIN: ensure_docker_running if [ -f /lib/systemd/system/docker.service ]; then systemctl start docker.service fi # END: ensure_docker_running # BEGIN: application_server_role if ! test -e /usr/bin/dockerd; then ensure_installed docker.io docker-compose-v2 fi mkdir -p /etc/systemd/system/docker.service.d/ if ! test -f /etc/systemd/system/docker.service.d/$(systemd-escape -p --suffix=mount "/mnt/external_storage/data").conf; then cat <<DROP_IN > /etc/systemd/system/docker.service.d/$(systemd-escape -p --suffix=mount "/mnt/external_storage/data").conf [Unit] Requisite=$(systemd-escape -p --suffix=mount "/mnt/external_storage/data") After=$(systemd-escape -p --suffix=mount "/mnt/external_storage/data") DROP_IN systemctl daemon-reload fi # END: application_server_role

ZFS datasets get the same protection, using the dataset's mountpoint from zfs get mountpoint. Use commands/check_mounts.sh to check that running containers see the right volumes.

Exit codes & human intervention#

CodeMeaning
0No error.
1Unspecified error: a command failed (set -e), a variable was unset, the YAML was invalid, the machine was not found, and so on.
101Human intervention required. The process stopped on purpose because continuing could destroy data.

honeyconf.sh never runs destructive commands on its own. When it reaches a disk that isn't set up yet, it stops with code 101 and prints the exact command for you to review and run:

************************************************************ Device /dev/sdb does not appear to be a LUKS device. If you are initializing a new device, please format the LUKS container using the following command: echo 'correct-horse-battery-staple' | cryptsetup --key-file - luksFormat /dev/sdb WARNING: All data will be lost! ************************************************************ PROCESS HALTED. Human intervention required
************************************************************ tank does not appear to be a zpool. If you are initializing a new device, please create a zpool using the following command: zpool create -O compression=lz4 -O atime=off tank /dev/sdb /dev/sdc ************************************************************ PROCESS HALTED. Human intervention required

After running the command, deploy again. Everything before the stopping point was already applied and is checked again quickly.

Security notes#

  • Secrets are plain text. machines.yaml holds LUKS keys, ZFS passphrases and TLS private keys. Keep it in a private repository, encrypted with a tool such as sops, git-crypt or ansible-vault, and decrypt it only to compile.
  • deploy.sh traces every command. It runs bash -vx, so secrets that appear in the script, such as cryptsetup passphrases and file contents, are printed to your terminal. Don't save deploy logs in shared CI output.
  • Secrets show up briefly in the process list. Passphrases are piped with echo, so other users on the target can see them in ps while the command runs.
  • Managed files are overwritten. authorized_keys, sudoers drop-ins and system.files are replaced on every deploy, so local changes are lost.
  • The SSH user is effectively root. Protect that account's key as if it were a root key.

The repository includes schema.json (JSON Schema 2020-12), which describes everything on this page. Use it for autocompletion and validation in your editor, or in CI.

Testing & contributing#

Running the tests

# In Docker (same as CI): bats, yq 4 and jq are preinstalled make test # Natively, with bats, yq and jq installed make test_native

Each emitter has a test/<emitter>.bats file that compiles a small machines.yaml and checks the output. test/integration/minimalist is a snapshot test of a whole compiled script. If you change any emitter output on purpose, update expected.sh in the same change.

Writing an emitter

  1. Create emitters/my_feature.sh. Source ../config.sh, read your keys, and exit 0 early when the feature isn't configured.
  2. Print idempotent bash wrapped in # BEGIN: my_feature / # END: my_feature.
  3. Call it from compile.sh at the right place in the order.
  4. Add your keys to schema.json, a test/my_feature.bats file, and a section on this page.
#!/bin/bash -eu pushd "$(dirname $0)" > /dev/null . ../config.sh popd > /dev/null timezone="$(config "system.timezone" | value)" if [ -z "$timezone" ]; then exit 0 fi cat <<EOF # BEGIN: timezone if [ "\$(timedatectl show -p Timezone --value)" != "${timezone}" ]; then timedatectl set-timezone ${timezone} fi # END: timezone EOF
